# 2026-5-5 大数据量采集死机问题分析与解决

## 1. 问题现象

基于日志 `log-20260505.txt`、`log-20260505-2.txt`、`log-20260506-1.txt`，在大数据量参数（典型：`4000Hz / 51200点 / PHASE`）下出现两类问题：

1. 运行几分钟后“无波形/假死”：
- 采集线程日志停止更新（不再有 `Dummy-*` 采集循环日志）；
- 主线程仍存活，持续打印 `Storage queue: 0/200`；
- 无 Python Traceback，属于运行期卡死/阻塞而非显式异常崩溃。

2. 关闭后再次启动无波形（部分场景需重启电脑恢复）：
- 启动流程显示成功，但无数据回调；
- `Storage queue` 长时间为 `0/200`；
- STOP 时线程可能难以及时退出。

## 2. 日志定位结论

### 2.1 运行期卡死定位

在 `log-20260505.txt` 与 `log-20260506-1.txt` 中，卡死前有一致模式：
- `query_buffer_points` 调用耗时逐步升高（数十毫秒上升到 100ms+）；
- `Slow loop iteration` 常态接近 1s，线程实时性余量不足；
- 随后采集线程日志中断，主线程仍存活。

结论：
- 首要问题是采集线程在运行期进入阻塞/停摆状态（高概率在底层驱动调用路径）。

### 2.2 二次启动无波形定位

`log-20260505-2.txt` 显示：
- 采集“启动成功”后无数据回调；
- 队列始终 `0/200`；
- STOP 阶段出现线程无法及时结束现象。

结论：
- 异常停机后，驱动/采集状态存在残留风险；
- 需要更稳健的停机顺序与运行期故障恢复机制。

## 3. 本次针对性代码优化

### 3.1 目标

优先降低“运行几分钟后死机”概率，并在发生卡死时自动恢复。

### 3.2 已完成改动

#### A. 去除强制杀线程路径，避免状态污染

文件：`src/acquisition_thread.py`、`src/main_window.py`

- `AcquisitionThread.stop()` 改为“仅请求停止（non-blocking）”；
- 新增 `wait_until_stopped(timeout_ms)`，只等待不 `terminate()`；
- `MainWindow._on_stop()` 与 `closeEvent()` 调整顺序：
  1) 请求线程停止；
  2) 调用硬件 `api.stop()`；
  3) 等待线程退出；
- 移除强杀线程逻辑，避免驱动/DMA资源异常残留。

#### B. 增加运行期“无数据超时”自动恢复

文件：`src/main_window.py`

- 新增参数：
  - `ACQ_STALL_TIMEOUT_S = 8.0`
  - `ACQ_RECOVERY_COOLDOWN_S = 20.0`
- 在 `_on_phase_data/_on_raw_data` 更新 `self._last_data_time`；
- 在 `_update_status()` 周期检测采集活性；
- 若采集中连续 8 秒无数据回调，则触发一次自动恢复：
  - `STOP -> 延时 800ms -> START`
- 增加恢复冷却，防止重复抖动。

## 4. 预期效果

1. 运行期采集停摆时，不再长期“挂死无波形”，可自动恢复；
2. 停机/退出过程更温和，降低二次启动无波形概率；
3. 日志中可见恢复触发点（`Acquisition stall detected...`），便于继续诊断底层驱动行为。

## 5. 后续建议

1. 若仍有少量恢复失败，下一步增加“软复位重连流程”：`stop -> close -> reopen -> reconfig -> restart`；
2. 对 `query_buffer_points/read_phase_data` 增加更细粒度耗时与返回码埋点，定位具体阻塞 API；
3. 进一步降低 UI 与采集耦合开销（降低主线程压力与长时抖动）。

## 7. 2026-05-06 复盘修正

结合 `log-20260506-1.txt`、`log-20260505.txt` 与当前代码，新的结论需要修正为：

1. 旧版优化解决了“保存线程回压”问题，但没有解决根因。
   - 旧版日志中，`Storage queue` 会从 `0/200` 持续爬升到 `25/200`，说明保存链路确实偏慢。
   - 新版日志中，长时间保持 `Storage queue: 0/200`，说明保存线程已不是当前主瓶颈。

2. 当前主因是“大块读数”本身过重。
   - 参数 `4000Hz / 51200点 / PHASE / 4000帧` 下，单次 `read_phase_data()` 读取量为：
     `6400(merge后点数) * 4000帧 = 25,600,000 int32`
   - 单块数据量约 `25,600,000 * 4 = 102.4MB`。
   - 这 100MB 级数据块每次都要经过：
     - DLL 侧 DMA/拷贝；
     - Qt 线程信号投递；
     - 主线程 `_on_phase_data`；
     - 保存线程写盘；
     - 可选 TCP 通信链路。

3. 日志与上述结论一致。
   - 新版死机前，`_on_phase_data` 常态 `150~190ms`；
   - `query_buffer_points` 上升到 `100~200ms`；
   - 采集循环常态接近 `1s`，随后采集线程日志停止；
   - 手动 STOP 后日志停在 `pcie7821.api : Stopping acquisition...`，说明 DLL/驱动停机调用也可能被同一类阻塞拖住。

4. 因此，“自动恢复”没有真正解决问题。
   - 它只能在“线程还能响应 stop/start”的前提下工作；
   - 一旦底层采集调用本身进入阻塞，主线程再调用 `api.stop()` 也可能一起卡住。

## 8. 修正后的解决方案

本次代码改为参数解耦，而不是强制上限：

1. `FrameLoad`：单次从 FPGA / DMA 读取的帧数；
2. `FramePlot`：单次用于时域图、PSD、Time-Space 更新的帧数；
3. 当前实现要求 `FramePlot <= FrameLoad`。

这样做的目的：

1. 让采集块大小和显示分析窗口独立调节；
2. 避免再把“采集压力”和“显示压力”绑在同一个参数上；
3. 为后续现场测试保留更直接的调参手段。

当前建议的现场使用方式：

1. 当 `FrameLoad` 过大导致 DLL/驱动调用变慢时，直接手动调小 `FrameLoad`；
2. 当只需要降低界面刷新和频谱分析负担时，调小 `FramePlot`；
3. 若将来需要 `FramePlot > FrameLoad`，则必须再增加跨采集块显示缓存层，当前版本未实现该能力。
