更重要的问题是实时读取边界：驱动缓冲多次积压到目标读取块的 `20x` 以上。这通常还不等于软件已经丢数据，但它说明上位机读取速度短时间内远低于硬件产数速度。如果驱动环形缓冲容量有限，继续积压就可能演变成底层覆盖或后续 DMA/驱动异常。

因此优化原则是：显示可以跳帧，采集和保存不能被显示拖慢。

## 5. 根因

### 5.1 采集线程承担了过重的显示快照生成

当前采集块为：

```text
scan_rate = 100000 Hz
Length/Load = 0.200 s
load_frames = 20000
PHASE crop = [100, 800) => 700 points/frame
single display block ~= 20000 * 700 * 4 = 53.41 MB
```

旧逻辑每个 200 ms 采集块都会把显示矩阵复制进显示历史；达到 `Length/Plot` 周期时，又会把 `0.4 s` 或 `1.0 s` 的历史窗口拼成一个新的大数组交给 GUI。

在 `Length/Plot = 1 s` 时，单个 GUI 快照约为：

```text
100000 frames * 700 points * 4 bytes ~= 267 MB
```

这个快照生成和内存复制发生在采集线程内，直接推高 `display_pub_ms`，进而拖慢 `read_phase_data()` 循环。

### 5.2 GUI 主线程对整块窗口做显示侧弧度转换

旧逻辑在 `_on_phase_data()` 中先把整个显示窗口从 `int32` 转为 `float32` 弧度，再进入波形、PSD、Time-Space 显示。

但实际绘图并不总需要整块窗口：

- Time 模式波形最多只画 4 帧。
- PSD 只需要最后一帧或一个空间点的时间序列。
- Space 模式只需要某一个 `Region` 的时间序列。
- Time-Space 自身会再做距离裁剪、空间降采样和时间降采样。

因此整块窗口转换会制造大量无效内存带宽和主线程 CPU 压力。

### 5.3 SPACE 模式使用 Python 循环抽取时间序列

旧逻辑通过 `for i in range(frame_num)` 逐帧计算 `idx = region_idx + point_num * i` 来抽取单点时间序列。在 40000 或 100000 帧窗口下，这会在 GUI 主线程中增加额外开销。该操作可以直接通过 NumPy reshape 后按列切片完成。

## 6. 已完成优化

### 6.1 显示历史不再每块强制复制

文件：`src/acquisition_thread.py`

修改后，采集线程仅在显示矩阵不是连续内存时才做 `np.ascontiguousarray()`，避免每个 `Length/Load` 块无条件复制几十 MB 显示数据。

### 6.2 GUI 未消费旧快照时，采集线程跳过新快照生成

文件：`src/acquisition_thread.py`

修改后，在准备拼接大显示窗口前先检查 `_latest_display_data`。如果 GUI 还没有消费上一帧，采集线程不再继续拼接新的大数组，而是记录 `gui_skips` 并返回。

这意味着：

- GUI 可能丢显示帧，这是允许的。
- 完整采集块仍然先进入保存/TCP 消费路径。
- 采集线程不会因为 GUI 主线程忙而连续堆积新的大快照。

### 6.3 弧度转换改为按实际渲染数据延迟执行

文件：`src/main_window.py`

修改后 `_on_phase_data()` 不再对整块显示窗口做全量 `int32 -> float32(rad)` 转换，而是将 `phase_scale = pi / 32767` 传入显示函数。真正渲染时才对最小必要数组做转换：

- Time 模式：只转换要画的最新几帧和 PSD 输入帧。
- Space 模式：只转换所选 `Region` 的时间序列。
- Time-Space：交给 Time-Space 控件在裁剪和降采样后再转换。

保存和 TCP 仍然接收原始采集块，不受显示侧弧度转换影响。

### 6.4 SPACE 模式改为向量化抽取

文件：`src/main_window.py`

单通道 SPACE 模式现在通过：

```python
matrix = np.asarray(display_data).reshape(frame_num, point_num)
raw_trace = matrix[:, region_idx]
```

直接抽取时间序列，不再在 GUI 主线程执行逐帧 Python 循环。

### 6.5 Time-Space 缩放后移

文件：`src/time_space_plot.py`

`TimeSpacePlotWidget.update_data()` 新增 `display_scale` 参数。控件在距离裁剪、空间降采样后才执行弧度缩放，显著减少 Tab2 激活时的无效转换量。

## 7. 风险边界

本次优化没有改变以下链路：

- `read_phase_data()` 的读取点数和读取块大小。
- `Length/Load` 的 DLL 读取节奏。
- 保存器 `save_block()` 入队入口。
- `.bin` / `.bz` 保存包聚合逻辑。
- Tab3 TCP ingest 入队逻辑。

因此本次改动的目标是降低显示路径对采集线程和 GUI 主线程的干扰，而不是降低采集数据量或保存数据量。

需要注意：显示帧跳过是设计行为。后续复测时，`gui_skips` 增加只表示 GUI 没有显示每一个快照，不代表采集或保存丢数据。判断保存完整性应看：

- `save_dropped`
- `Save enqueue failed`
- `.bz raw_queue/packet_queue/compressed_queue`
- `packet_queue_full`
- `compressed_queue_full`
- `compression_not_realtime`
- 保存停止摘要中的 `dropped`

- PCIe API 支持返回 DMA 视图；采集线程在裁剪后只复制最终有效数据，避免先复制完整 DMA 块再裁剪。
- 诊断新增 buffer_ratio、backlog_s、真实 gui_interval_ms 和快照类型/大小。

离屏仿真 3.5 s 共收到 8 次显示回调，最后间隔约 415 ms、最大约 433.5 ms，证明 0.4 s 唤醒与 GUI 消费链路在无硬件瓶颈时可以达到目标。真实硬件结果仍以新日志为准。

## 11. 数据存储预检

针对同一现场参数 Length/Load=0.2 s、单块约 53.41 MiB，已提前测试保存链路：

- .bin：3 块共 160.22 MiB 全部写入，文件字节数完全一致，本机临时盘实测约 1306.6 MiB/s。
- .bz 0.2 s 包：单包输入 53.41 MiB，压缩约 585.5 ms，CRC 和逐点解压一致。
- .bz 4 worker 持续测试：5 块共 267.03 MiB，全部入队、无丢块、逐包 CRC 和逐点校验通过；总有效输入处理约 171 MiB/s。
- .bz 默认 1 s 包：输入 267.03 MiB，文件 133.62 MiB，压缩约 2683.5 ms，总排空约 3.08 s，CRC 和逐点校验通过。

结论：.bin 在本机测试中余量充足；NumPy Bitshuffle .bz 在 700 点、100 kHz、Save DS=1 的最重配置下压缩速度低于约 267 MiB/s 输入速率，短测可以依靠并行和队列无损排空，但不能据此保证长时间实时。长时间完整采集应优先使用 .bin，或提高 Save DS 后再验证 .bz。

为避免存储引发与显示类似的内存压力，运行时队列已从固定 200 块改为按实际 block/packet 字节数和可用内存计算。旧配置在 53.41 MiB/块时仅 raw queue 理论上可达约 10.68 GiB；新配置总队列预算上限为 1.5 GiB，并按 raw/packet/compressed 三阶段分配。日志新增 input_mib_s、queue_mb、raw_backlog_s 和 .bz worker 工作集估算。

保存完整性还增加两项保护：

- 数组成功入队后设为只读，防止保存线程尚未消费时被其他异步消费者误改；队列满、入队失败时恢复原写权限。
- .bin 停止保存不再等待 5 秒后强行关闭文件，而是等待保存线程排空。回归测试故意让单次写盘阻塞 5.2 秒，最终文件仍逐点完整。
