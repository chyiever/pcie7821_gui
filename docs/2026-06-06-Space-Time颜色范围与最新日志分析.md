# Space-Time 颜色范围修复与最新测试日志分析

## 1. 分析范围

本次分析依据最新测试日志 `logs/log--20260606-2.txt`，并检查了 `src/time_space_plot.py`、`src/main_window.py`、`src/acquisition_thread.py` 和 `src/data_saver.py` 中的显示、采集和保存逻辑。分析重点包括 Space-Time 图颜色范围无法由前面板控制的问题，以及上一轮采集显示通路优化后仍然存在的性能和可靠性问题。

## 2. Space-Time 颜色范围问题

Space-Time 图创建时，`HistogramLUTWidget` 已经通过 `setImageItem()` 与 `ImageItem` 建立关联。旧代码在每次图像刷新时再次调用 `setImageItem()`。重新绑定会使 Histogram 重新处理图像和 levels，可能触发自动范围行为，因此即使前面板已经设置 `vmin` 和 `vmax`，颜色条范围仍可能在后续更新中变化。

本次修改将 `setImageItem()` 限制在颜色条创建阶段，只绑定一次。每次图像刷新时使用 `autoLevels=False`，并通过统一的 `_apply_color_levels()` 把前面板中的固定范围应用到图像和颜色条。颜色条的 level 区域设置为不可拖动，避免颜色条交互反向覆盖前面板参数。`vmin` 和 `vmax` 的输入精度由三位小数提高到六位小数，以便配置较小的 Phase 弧度颜色范围。

加载本地参数时，旧逻辑会依次设置 `vmin` 和 `vmax`。如果新 `vmin` 暂时大于旧 `vmax`，输入校验可能先修改 `vmin`，导致最终范围与保存参数不一致。本次改为原子加载两个值，在确认 $v_{\min} < v_{\max}$ 后一次更新内部状态和控件。

## 3. Space-Time 更新逻辑的其他检查结果

Space-Time 数据仅在 PLOT 开启并且 Tab2 为当前活动页时更新，这一逻辑可以避免隐藏页面持续绘图。数据首先按距离范围裁剪，再进行时间和空间降采样，最后转为 `(space, time)` 排列并写入滚动显示缓冲，坐标轴语义正确。

当前滚动缓冲写满后，会移动整个历史显示缓冲再追加新块。该操作的成本会随 `window_frames`、空间范围和降采样后的显示尺寸增加。当前日志中的显示更新时间通常只有约 $2\ \mathrm{ms}$，因此该问题尚未成为主要瓶颈，但如果后续增大窗口或降低降采样倍数，建议进一步改为环形缓冲，避免每次移动完整历史数据。

旧代码在每次显示更新时都会复制有效显示区域。本次优化为：当显示缓冲已经写满时直接使用连续的完整缓冲区，只在缓冲尚未写满、有效列是非连续切片时执行连续化复制。

如果启用了 Phase 软件空间裁剪，Space-Time 接收到的数据点索引是裁剪后的相对索引，而当前纵轴仍按相对索引显示。若现场需要显示原始光纤绝对点号，后续应将裁剪起点偏移传递给 Space-Time 坐标映射。

## 4. 最新日志中的改善情况

上一轮“完整数据与 GUI 显示解耦”的优化已经产生明显效果。Raw GUI 回调通常只需要约 $2$ 至 $4\ \mathrm{ms}$，并且在 GUI 未及时消费显示数据时，`gui_skips` 会增长，说明旧显示快照被覆盖而不是进入无上限 Qt 队列。十四次 STOP 记录中，采集线程停止延迟约为 $5.5$ 至 $124.6\ \mathrm{ms}$，不再出现停止信号被历史 Raw 回调拖延数秒的情况。

保存队列在正常磁盘状态下保持稳定。日志中的 `save_dropped` 始终为零，保存队列历史最大值通常只有三块，Phase 稳定采集阶段的单次写盘时间通常约 $20$ 至 $33\ \mathrm{ms}$。这说明正常状态下磁盘保存线程不是 Phase 采集的主要瓶颈。

## 5. 最新日志暴露的剩余问题

### 5.1 Raw 底层读取性能仍然不稳定

对于 `Points=20480`、`FrameLoad=1024` 的 Raw 数据，单块大小为 $40\ \mathrm{MiB}$，数据产生周期为 $512\ \mathrm{ms}$。部分启动轮次的单次读取中位数达到约 $2.05$ 至 $2.32\ \mathrm{s}$，最大值超过 $3.4\ \mathrm{s}$，驱动缓冲区最终达到约 $1.07 \times 10^9$ 点。相同参数的首轮测试却可以出现约 $62\ \mathrm{ms}$ 的读取时间，说明 Raw 读取性能不仅受块大小影响，还可能与驱动内部状态、启动轮次或历史缓冲区状态有关。

对于 `Points=51200`、`FrameLoad=1024` 的 Raw 数据，单块达到 $100\ \mathrm{MiB}$。其读取时间最大达到约 $9.13\ \mathrm{s}$，并出现约 $261\ \mathrm{ms}$ 的缓冲区查询耗时。该参数要求持续处理的数据率约为：

$$
\frac{100\ \mathrm{MiB}}{0.512\ \mathrm{s}}
\approx 195.3\ \mathrm{MiB/s}
$$

因此不建议以该参数作为长期稳定采集配置。现场测试应降低 Raw `FrameLoad`，并比较每次启动后的首个读取块、稳定阶段读取耗时和驱动缓冲区增长趋势。如果相同参数在重新启动后性能差异仍然很大，需要进一步检查 DLL 或驱动停止后是否真正清空内部缓冲区，以及是否需要完整关闭并重新打开设备。

### 5.2 Phase 弧度转换仍占用较多 GUI 时间

Phase 稳定采集阶段中，DLL 读取通常只需要约 $20$ 至 $45\ \mathrm{ms}$，但 GUI 的弧度转换中位耗时约为 $61\ \mathrm{ms}$，多数 Phase GUI 回调总耗时为 $50$ 至 $75\ \mathrm{ms}$。旧逻辑将完整 `int32` 显示块转换为 `float64`，会扩大内存带宽和临时内存占用。

本次将显示侧弧度转换改为 `float32` 原位乘法。Phase 原始保存数据仍保持 `int32`，只有显示快照使用 `float32`。该修改可减少约一半的显示浮点内存占用，并降低转换耗时。现场需要用下一轮日志比较 `rad_ms` 的中位数和最大值。

### 5.3 磁盘空间耗尽后持续报错

日志中共有 80 条 ERROR，全部为 `No space left on device`。旧保存线程在每次写盘失败后继续处理下一块，因此约每秒重复输出一次错误，同时继续接受保存数据。

本次最终修改采用“磁盘满时暂停保存、采集继续、空间恢复后自动续存”的状态机。保存线程检测到 `ENOSPC` 或 Windows 磁盘空间不足错误后，不会停止数据采集，也不会退出保存工作线程。保存器会关闭发生错误的文件、清空已有保存队列，并在暂停期间直接丢弃新到达的数据块，避免内存队列持续增长。主界面显示 `Save: Paused (disk full)`，同时保留采集、显示和 TCP 通路。

保存工作线程每隔约 $2\ \mathrm{s}$ 尝试创建下一个编号文件并恢复写入。磁盘完全写满时，操作系统仍可能允许创建文件但无法写入数据，因此磁盘满期间可能持续生成按编号递增的 `0 KB` 文件；下一次写入失败后，保存器再次进入暂停并继续尝试下一个编号。磁盘释放出空间后，新数据会直接写入当前恢复文件并继续正常保存。采用新编号文件恢复而不是继续写故障文件，可以明确区分磁盘写满前后的数据段，并避免部分写入导致的数据块边界不确定。暂停期间的数据无法补写，均计入 `dropped_blocks`。

### 5.4 Raw 保存格式会被错误扩大

旧保存器会把所有非 `int32` 数组转换为 `int32` 后写盘，因此 Raw `int16` 数据会被扩大一倍。这会增加 Raw 保存带宽和磁盘占用，也与“保存原始 Raw 数据”的语义不一致。本次修改为保持采集数据原始 dtype：Raw/IQ 按 `int16` 写盘，Phase 按 `int32` 写盘。对应的离线读取程序必须根据数据源选择正确 dtype。

### 5.5 慢循环警告阈值不合理

旧采集线程只要单次循环超过 $100\ \mathrm{ms}$ 就记录 `Slow loop iteration`。但是采集循环本身需要等待一个 `FrameLoad` 数据块形成。例如 `ScanRate=2000`、`FrameLoad=2000` 时，正常循环周期就是 $1000\ \mathrm{ms}$。因此日志中大量约一秒的慢循环警告并不代表异常。

本次将慢循环阈值调整为：

$$
T_{\mathrm{warning}} =
\max(100\ \mathrm{ms}, 1.5 \times T_{\mathrm{block}})
$$

只有循环耗时显著超过正常数据块周期时才输出警告，可以明显降低误报警告数量。

## 6. 后续建议

下一轮现场测试应分别验证 Raw 和 Phase。Raw 测试建议从较小的 `FrameLoad` 开始，记录相同参数多次 stop/start 后的读取时间差异，并重点观察驱动缓冲区是否持续增长。Phase 测试应比较修改前后的 `rad_ms`，同时验证 Space-Time 前面板颜色范围在持续更新期间保持固定。

磁盘保存测试应准备足够空间，并额外安排一次受控的磁盘空间不足测试，确认保存线程只报告一次致命错误、界面显示保存已停止，而采集与显示仍能继续运行。由于 Raw 保存格式已改为原始 `int16`，相关离线读取工具需要同步确认 dtype。
