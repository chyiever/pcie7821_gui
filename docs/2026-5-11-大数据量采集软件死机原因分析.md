## 2. 现象复盘

在 `4000Hz / 51200点 / PHASE / FrameLoad=4000 / 实时存储开启` 的测试中，日志呈现出比较一致的模式：

1. 采集运行初期可以持续收到数据。
2. `query_buffer_points` 耗时逐步升高，后期常到 `80~200ms`。
3. `_on_phase_data` 主线程处理常态达到 `150~190ms`。
4. 单次采集循环 `Slow loop iteration` 常态接近 `0.9~1.2s`。
5. 随后采集线程日志停止，只剩主线程每 5 秒打印一次 `Storage queue: 0/200`。
6. 手动点击 `STOP` 后，日志停在 `pcie7821.api : Stopping acquisition...`，未见 `Acquisition stopped in ... ms`。

这说明：

- 主线程没有整体崩溃，Qt 定时器还在工作。
- 保存队列没有堆积，磁盘保存不是主瓶颈。
- 真正停住的是“采集线程 / DLL 调用 / 驱动状态机”这条链路。

## 3. 当前最可能的根因排序

### 3.1 首要怀疑：单次采集块过大，导致 DLL 或驱动进入长时间阻塞

当前测试参数下：

- `51200点 / merge=8` 后为 `6400` 个 PHASE 点
- `FrameLoad=4000`
- 单次 `read_phase_data()` 读取量：
  - `6400 * 4000 = 25,600,000` 个 `int32`
  - 约 `102.4MB / block`
- 单次采集块时间跨度：
  - `4000 / 4000Hz = 1.0s`

这意味着每次回调都在搬运一块约 100MB 的大数组，而且这 100MB 还要继续经过：

1. DLL 内部缓冲区到 Python 对齐缓冲区
2. NumPy `copy()`
3. Qt 跨线程信号投递
4. GUI 线程 `_on_phase_data`
5. 保存线程排队与写盘
6. 可选 TCP 打包/发送

如果底层 DLL 或驱动在高负载下存在“长时间不返回”或“内部锁等待”问题，`FrameLoad=4000` 会把这种风险明显放大。

### 3.2 第二怀疑：采集线程在 `query_buffer_points()` 或 `read_phase_data()` 中阻塞

从现有日志只能确认“采集线程最后还活着时，查询和读数都已经明显变慢”，但还不能区分卡死发生在：

- `query_buffer_points()`
- `read_phase_data()`
- `read_monitor_data()`
- `Qt signal emit` 后的数据链路

不过结合卡死后仍然只剩主线程定时日志，且手动 `STOP` 又停在 DLL `stop()` 上，更像是：

- 采集线程卡在 DLL 内部调用；
- 主线程随后调用 `pcie7821_stop()` 时，也被同一底层状态阻塞。

### 3.3 第三怀疑：主线程处理过慢，反过来放大了采集侧压力

`_on_phase_data` 在大块数据下长期 `150~190ms`，虽然这还不是“秒级”，但它至少说明：

- 大数组进入 GUI 线程后，处理代价已经不低；
- 若同时开启：
  - 波形显示
  - PSD
  - Time-Space
  - 实时保存
  - TCP 发送

则主线程和后台线程都会持续收到大块数据，系统整体余量很小。

不过这不是最核心根因，因为：

- 如果主线程是主瓶颈，保存队列、TCP 队列或 GUI 更新丢帧通常会先明显堆积；
- 目前最醒目的异常仍是 DLL 查询/读数逐渐变慢并最终疑似阻塞。

### 3.4 第四怀疑：`STOP` 与采集线程同时访问 DLL，卡住时会互相等待

当前结构是：

1. 主线程请求 `acq_thread.stop()`
2. 主线程立即调用 `api.stop()`
3. 采集线程可能仍在 `query_buffer_points()/read_phase_data()` 中

`src/pcie7821_api.py` 内所有 DLL 调用都受同一把 `threading.Lock` 保护。若采集线程在锁内 DLL 调用迟迟不返回，则：

- 主线程调用 `api.stop()` 也会等待这把锁；
- 即使采集线程已经收到“停止请求”，也无法马上退出；
- 日志就会停在 `Stopping acquisition...`

所以日志里看到的“点 STOP 后也像死机”，不一定是单独的 stop 逻辑问题，更可能是采集线程先卡住后把 stop 也拖住了。

## 4. 为什么上一版优化没有解决

上一版优化主要解决了两件事：

1. 去掉强制 `terminate()`，避免驱动状态污染；
2. 加了“无数据超时自动 stop/start 恢复”。

这两项都只能处理“线程还能响应”的情况。

如果根因是：

- 采集线程卡在 DLL 内部调用不返回；
- 或 DLL/驱动在高负载下内部状态异常；

那么：

- 自动恢复不会真正触发到可执行阶段；
- 主线程 `api.stop()` 也可能一起卡住；
- 所以“自动恢复”只能改善轻度停摆，不能解决这次的大块读数卡死。

## 5. 2026-05-11 的判断结论

当前最可能的结论是：

1. 根因仍在底层采集链路，而不是保存链路。
2. 触发条件与 `FrameLoad` 过大高度相关。
3. `FrameLoad=4000` 对 20km/6400 点 PHASE 数据来说单块太重，明显增大 DLL/驱动阻塞概率。
4. GUI、保存、TCP 可能会增加总压力，但更像“放大因素”，不是首因。
5. 现有日志还缺少“最后一次成功卡在哪个阶段”的精确信息，需要补采集链路埋点。

5. 卡死或点击 STOP 前的采集快照：
   - 当前阶段

本次代码修改正是围绕这些点增加日志。

## 7. 现阶段建议

在拿到下一轮更完整日志前，参数上应优先遵循：

1. 优先压低 `FrameLoad`，先解决单块过大问题。
2. `FramePlot` 独立于 `FrameLoad` 设置，只保留必要显示窗口。
3. 测试时优先关闭不必要的显示与通信路径，逐项增加负载：
   - 先保存
   - 再开波形/PSD
   - 最后再开 TCP

如果下一轮日志显示卡死前最后阶段长期停在：

- `query_buffer_points`：更偏向驱动缓冲区查询阻塞。
- `read_phase_data`：更偏向大块 DMA/拷贝阻塞。
- GUI slot：再回头压显示、TCP 或保存链路。
