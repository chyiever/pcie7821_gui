## 7. 已执行的软件优化

### 7.1 降低 GUI Phase 显示发布频率

文件：`src/acquisition_thread.py`

原逻辑每个 200 ms 采集块都会拼接显示窗口并发布最新 GUI 快照。对于当前 `length_plot_s=1.000`、`block_duration=200 ms` 的配置，这会导致大量重复的数组拼接和主线程覆盖。

优化后：

- 采集线程仍保留最近显示历史，不影响存储数据完整性
- GUI 快照发布频率按 `max(MIN_GUI_UPDATE_INTERVAL_MS, length_plot_s)` 限流
- 当前配置下从每 200 ms 发布一次降为约每 1 s 发布一次
- 减少 `np.concatenate`、拷贝和 GUI 覆盖压力
- 保持采集/存储原始数据路径不被降采样

### 7.2 监测波形按 UI 状态读取

文件：`src/acquisition_thread.py`、`src/main_window.py`

原逻辑在 Phase 模式下即使监测波形未显示，采集线程仍会读取 monitor 数据。优化后：

- 新增 `monitor_plot_enabled` 到采集线程配置
- UI 勾选状态变化时实时通知采集线程
- 未启用监测波形时跳过 `api.read_monitor_data()`
- 日志和诊断快照记录 `monitor_read_enabled` 和 `monitor_ms`

这可以减少采集循环内不必要 API 调用，降低与主数据读取竞争的可能。

### 7.3 拆分采集线程分段耗时诊断

文件：`src/acquisition_thread.py`、`src/main_window.py`

新增采集诊断字段：

- `last_api_read_ms`
- `last_crop_ms`
- `last_dispatch_ms`
- `last_display_publish_ms`
- `monitor_read_enabled`

周期性 `Acq status` 日志也增加 API 读取、分发和 GUI 发布耗时。后续复测可直接判断瓶颈是在 API 读取、数组裁剪、GUI 发布，还是下游回调。

### 7.4 调整 `.bz` 实时性指标语义

文件：`src/data_saver.py`、`src/main_window.py`

原逻辑将单包压缩耗时超过采集时长计入 `compression_not_realtime`。优化后：

- 单包慢压缩计入 `slow_compression_packet_count`
- `compression_not_realtime_count` 只用于队列满、压缩/打包失败、明确造成实时链路风险的事件
- 慢压缩 warning 按时间节流，避免日志刷屏
- UI 中区分 `slow` 与 `notRT`
- 有 drop、队列满、notRT 时显示红色；只有慢包时显示橙色

这样可以将“压缩慢但队列健康”和“实时存储已经失效”区分开。

## 10. 2026-08-13 实时链路追加优化

针对“存储不要出现大延时”的目标，本次进一步调整采集线程到保存线程之间的实时链路。核心原则是不把队列满时的压力直接转换为静默丢数据，而是减少采集线程内的同步重处理，让保存入队尽早完成，并让后续日志能直接判断保存是否拖慢采集。

### 10.1 保存入队优先

文件：`src/main_window.py`

原完整数据回调中，采集线程会先执行 Tab3 TCP 通信聚合，再执行本地保存入队。这样当 TCP 聚合、数组拼接或通信参数处理偶发变慢时，会推迟保存入队，也会推迟下一轮采集读取。

优化后：

- 完整采集块进入 `_handle_full_data_block` 后，优先调用 `saver.save_block(data)`。
- 保存入队完成后，才把 Phase 数据交给 TCP ingest 队列。
- 新增 `save_enqueue_ms/max` 和 `tcp_enqueue_ms/max` 诊断，后续可直接判断采集线程是否卡在保存入队或 TCP 入队。

### 10.2 存储降采样移入保存线程

文件：`src/data_saver.py`、`src/main_window.py`

原逻辑在采集线程中执行存储专用降采样，然后再入队保存。对大块数组来说，这仍然会占用采集线程 CPU 和内存带宽。

优化后：

- 采集线程只把原始完整块引用入队给保存器。
- `.bin` 和 `.bz` 保存线程内部根据 `source_points_per_frame` 和 `storage_downsample_factor` 做帧级点抽取。
- 保存文件名和文件头仍使用最终保存点数 `points_per_frame`，离线解析格式不变。
- 新增 `last_enqueue_ms`、`max_enqueue_ms`、`source_points_per_frame`、`storage_downsample_factor` 保存诊断字段。

### 10.3 TCP ingest 后台化

文件：`src/tcp_tab3/tcp_tab3_manager.py`

原逻辑中，TCP 的 Length/Comm 聚合和数据复制发生在采集线程回调里。优化后新增 TCP ingest 后台线程：

- 采集线程只把 Phase 块放入 TCP ingest 队列。
- Length/Comm 聚合、通信包准备和发送线程入队在 TCP 后台线程中完成。
- TCP ingest 队列满时丢弃最旧通信块，保护采集和本地保存优先级；这只影响 Tab3 通信，不影响本地保存。
- 新增 `tcp_ingest_queue`、`tcp_ingest_dropped`、`tcp_ingest_ms`、`tcp_process_ms` 诊断字段。

### 10.4 预期复测表现

本次优化后，同参数复测应重点观察：

1. `dispatch_ms` 是否明显下降，尤其是保存开启且 TCP 开启时。
2. `save_enqueue_ms` 是否保持在毫秒级以下，`save_enqueue_internal_ms` 是否稳定。
3. `tcp_process_ms` 即使偶发偏高，也不应显著推高 `dispatch_ms`。
4. 驱动缓冲积压峰值应低于此前的 32.65 s，后半段 p95 应下降。
5. 本地保存仍应保持 `save_dropped=0`、`packet_queue_full=0`、`compressed_queue_full=0`。
