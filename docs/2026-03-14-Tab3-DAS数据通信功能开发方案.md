# Tab3 DAS 数据通信功能开发方案

日期：2026-03-14
更新：2026-07-29 Length/Comm 参数模型

## 1. 目标

Tab3 用于把 PCIe-7821 采集到的 DAS PHASE 数据按 `wb-monitor` 的 DAS TCP 接收协议实时发送到服务器端。当前实现定位为发送端，不负责接收端绘图或定位分析。

核心目标如下：

- Tab3 独立配置通信参数与显示通信状态。
- 通信功能默认启用，开始采集后自动建立发送会话。
- 只支持 `单通道 + PHASE` 数据源，避免协议语义和数据矩阵形态不一致。
- 发送原始 `int32` 相位计数，接收端恢复为 `rad`，使用未滤波相位数据。
- 支持空间通道范围裁剪、空间降采样和时间降采样。
- 以 `Length/Comm` 控制每个 TCP 数据包对应的采集时长。
- 数据包格式与 `wb-monitor/src/das_tab3/das_tcp_server.py` 当前协议兼容。

## 2. 接收协议

接收端固定包头格式为：

```text
>IIIId
```

包头长度为 `24` 字节，字段顺序如下：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `comm_count` | `uint32` | 当前采集会话内的通信包序号，从 0 开始递增。 |
| `sample_rate_hz` | `uint32` | 时间降采样后的有效采样率。 |
| `channel_count` | `uint32` | 空间裁剪和空间降采样后的通道数。 |
| `data_bytes` | `uint32` | 包体字节数。 |
| `packet_duration_seconds` | `float64` | 当前包体覆盖的时间长度。 |

包体为小端 `int32`（x86 本机字节序），排列方式为 channel-major：先发送第 0 个空间通道的全部时间样本，再发送第 1 个空间通道的全部时间样本，依次类推。接收端按下面规则恢复矩阵：

```text
samples_per_channel = round(sample_rate_hz * packet_duration_seconds)
matrix.shape = (channel_count, samples_per_channel)
```

## 3. 数据源与单位

通信数据来自采集线程输出的完整 PHASE 数据块，不从 GUI 绘图数据中取数。这样可以保证通信不受 `Length/Plot`、波形刷新节流或 GUI 是否及时消费快照的影响。

数据语义如下：

- 输入：单通道 PHASE `int32` 数据。
- 单位转换：发送端直接发送原始 `int32` 相位计数，不在此端做弧度换算；接收端按 `phase_rad = phase_int32 / 32767.0 * pi` 恢复弧度。
- 滤波：不发送 Tab1/Tab2 Filter 后的数据。
- 空间范围：只发送用户配置的通道起止范围。

## 4. Length/Comm 包长模型

当前版本新增 `Length/Comm` 参数，位于 Tab3，默认 `1 s`。它决定每个 TCP 数据包覆盖的原始采集时长。

软件运行时按扫描率换算：

```text
comm_frames = Length/Comm * ScanRate
load_frames = Length/Load * ScanRate
```

约束：

```text
Length/Comm 必须是 Length/Load 的整数倍
comm_frames 必须是整数帧
```

原因是采集线程每次只输出完整 `Length/Load` 块，Tab3 管理器只能在完整采集块边界上聚合通信包。默认 `ScanRate=2000 Hz` 时：

```text
Length/Load = 0.2 s -> 400 frames
Length/Comm = 1.0 s -> 2000 frames = 5 个采集块
```

也就是说，Tab3 会缓存 5 个完整采集块，然后组成 1 个 TCP 包交给发送线程。

## 5. 发送矩阵构造

采集线程传入的数据按时间优先理解：

```text
frame_matrix.shape = (frame_num, point_num_after_merge_or_crop)
```

Tab3 发包前先按 `Length/Comm` 聚合到：

```text
comm_matrix.shape = (comm_frames, point_num_after_merge_or_crop)
```

然后执行空间裁剪：

```python
selected = comm_matrix[:, channel_start:channel_end + 1]
```

再执行空间降采样：

```python
selected = selected[:, ::space_downsample]
```

协议要求 channel-major，因此先转置：

```python
send_matrix = selected.T
```

得到：

```text
send_matrix.shape = (channel_count, comm_frames)
```

最后执行时间降采样：

```python
send_matrix = send_matrix[:, ::time_downsample]
```

最终矩阵为：

```text
send_matrix.shape = (channel_count, samples_per_channel)
```

## 6. 单包数据长度由什么决定

TCP 包总长度由固定包头和包体组成：

```text
tcp_packet_bytes = 24 + payload_bytes
payload_bytes = channel_count * samples_per_channel * 4
```

其中：

```text
samples_per_channel = comm_frames / TimeDownsample
channel_count = ceil(selected_space_points / SpaceDownsample)
comm_frames = Length/Comm * ScanRate
```

因此通信包大小由这些参数决定：

| 参数 | 影响 |
| --- | --- |
| `Length/Comm` | 决定每包覆盖多少原始采集帧。 |
| `ScanRate` | 与 `Length/Comm` 一起决定 `comm_frames`。 |
| `TimeDownsample` | 减少每个通道的时间样本数，同时改变包头中的有效采样率。 |
| `channel_start/channel_end` | 决定参与发送的空间点范围。 |
| `SpaceDownsample` | 减少发送的空间通道数。 |
| `Merge` 和 PHASE 裁剪 | 决定进入通信链路前可用的空间点数。 |

这些参数不参与 TCP 包大小：

- `Length/Plot`：只影响 GUI 显示窗口。
- `Length/Save`：只影响保存包时长。
- `Length/File`：只影响保存文件轮转时长。
- `Save DS`：只影响落盘数据抽点，不影响通信。
- BZ 压缩参数：只影响 `.bz` 保存，不影响通信。

示例：

```text
ScanRate = 2000 Hz
Length/Comm = 1 s
TimeDownsample = 2
空间裁剪后 1000 点
SpaceDownsample = 5
```

则：

```text
comm_frames = 2000
samples_per_channel = 1000
channel_count = 200
payload_bytes = 200 * 1000 * 4 = 800,000 bytes
tcp_packet_bytes = 800,024 bytes
packet_duration_seconds = 1000 / 1000 = 1 s
```

## 7. 包头字段计算

当前发送线程使用以下规则生成包头：

```text
comm_count = current_session_packet_index
sample_rate_hz = ScanRate / TimeDownsample
channel_count = send_matrix.shape[0]
data_bytes = channel_count * samples_per_channel * 4
packet_duration_seconds = samples_per_channel / sample_rate_hz
```

`TimeDownsample` 必须整除 `ScanRate`，否则 `sample_rate_hz` 无法作为整数可靠写入 `uint32` 包头，接收端按 `round(sample_rate_hz * packet_duration_seconds)` 恢复样本数时也容易出现误差。

包体序列化方式：

```python
payload = np.ascontiguousarray(send_matrix, dtype=np.int32).reshape(-1).tobytes()
```

## 8. 当前代码结构

相关模块如下：

| 模块 | 职责 |
| --- | --- |
| `src/tcp_tab3/tcp_types.py` | 定义 `CommSettings`、`CommContext`、发送结果和状态类型。 |
| `src/tcp_tab3/tcp_packet_builder.py` | 完成 `int32` 序列化、裁剪、降采样、包头和 payload 构造。 |
| `src/tcp_tab3/tcp_client.py` | 负责 socket 连接、重连和底层发送。 |
| `src/tcp_tab3/tcp_sender_worker.py` | 后台线程，串行消费待发送队列，避免阻塞 GUI。 |
| `src/tcp_tab3/tcp_tab3_manager.py` | 管理 Tab3 会话、可用性判断、Length/Comm 聚合、队列背压和统计。 |
| `src/main_window.py` | 创建 Tab3 控件，采集开始/停止时同步参数并向管理器推送 PHASE 数据。 |

## 9. 可用性判断

Tab3 只有在满足以下条件时才发送：

- 通信启用开关为开启。
- 当前为单通道采集。
- 当前数据源为 PHASE。
- `Length/Comm` 是 `Length/Load` 的整数倍。
- 通道范围和降采样参数有效。
- TCP 发送线程已启动。

如果不满足条件，界面应显示明确原因；采集本身不应因为通信不可用而被阻断。

## 10. 背压策略

通信链路使用后台队列，不在 GUI 线程或采集线程中执行阻塞式网络发送。若下游服务器、网络或接收端处理速度不足，发送队列可能累积。为保证采集实时性，队列满时应优先丢弃旧通信包，并在界面统计和日志中暴露丢包数量。

该策略意味着 Tab3 是实时监视链路，不是可靠归档链路。需要完整数据时，应使用 `.bin` 或 `.bz` 保存。

## 11. 与旧方案的差异

旧方案默认“每个采集回调就是一个通信包”，通信包时长实际等于 `FrameLoad / ScanRate`。这导致用户想调整通信包长度时，只能间接改采集读取粒度，容易把网络包大小和 DLL 读取风险绑在一起。

当前方案把通信包长独立为 `Length/Comm`：

| 旧口径 | 新口径 |
| --- | --- |
| 每个 `FrameLoad` 回调直接发包。 | 多个 `Length/Load` 块聚合到 `Length/Comm` 后发包。 |
| 通信包长由采集读取帧数间接决定。 | 通信包长由 Tab3 的 `Length/Comm` 直接决定。 |
| 想改网络包大小会同时改变 DLL 单次读取大小。 | 可以在保持 `Length/Load` 较小的同时，把通信包设为 1 s 或其他整数倍。 |
| `FramePlot` 与通信无关但容易被误解。 | 文档和 UI 明确 `Length/Plot` 只属于显示链路。 |

## 12. 验证重点

本功能修改后至少需要验证：

- 单通道 PHASE 模式下，默认 `Length/Comm=1 s` 能稳定发送。
- `Length/Comm=Length/Load` 时，每个采集块对应一个 TCP 包。
- `Length/Comm` 大于 `Length/Load` 时，只有累计到完整通信包才入发送队列。
- 非整数倍配置会被拒绝，不会发送半包或错位矩阵。
- `TimeDownsample`、`SpaceDownsample` 和通道范围变化后，接收端恢复出的矩阵维度与预期一致。
- 关闭显示或调整 `Length/Plot` 不改变 TCP 包大小。
- 改变 `Length/Save` 或 `Length/File` 不改变 TCP 包大小。
