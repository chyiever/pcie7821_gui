# 20260814 大数据量 DAS 上位机软件开发经验总结文档

本文面向后续开发者，基于本项目近期现场日志、测试分析文档、开发日志和当前源码实现，总结大数据量 DAS 上位机在实时采集、波形刷新、数据保存、界面响应、通信转发和诊断日志方面形成的工程经验。

本文不是用户操作说明，而是开发经验复盘。重点回答四个问题：怎样让波形和 Time-Space 显示尽量流畅；怎样保证采集与保存链路尽量不丢数据；怎样避免 GUI、STOP、保存或通信把软件拖死；怎样设计数据流和日志，便于现场快速判断问题发生在哪一层。

相关源码主要包括 `src/acquisition_thread.py`、`src/main_window.py`、`src/data_saver.py`、`src/time_space_plot.py`、`src/pcie7821_api.py`、`src/tcp_tab3/tcp_tab3_manager.py`、`tests/test_display_snapshot_cadence.py` 和 `tests/test_data_saver_integrity.py`。参考文档包括 2026-08-12 至 2026-08-14 的日志分析文档、`docs/100kHz采样数据量减半日志分析文档.md`、存储技术说明和 2026-05 大数据量卡死复盘文档。

## 1. 总体结论：采集优先、显示可丢、保存可验、问题可定位

本项目多轮问题都指向同一个架构原则：采集线程不能被 GUI 绘图、频谱分析、Time-Space 全窗口处理、TCP 打包、压缩或磁盘写入长期阻塞。完整采集数据必须优先进入保存/通信入口；显示只消费最新快照，允许跳帧，不允许排队拖慢采集。

这条原则来自多个现场现象：

- 2026-05 大数据量测试中，`4000Hz / 51200点 / PHASE / FrameLoad=4000` 单块约 `102.4 MB`，底层 DLL 查询/读数逐步变慢，最终采集线程疑似卡在 DLL 调用内。保存队列并非主瓶颈。
- 2026-06 Raw 大块显示卡顿中，完整 `40 MiB` Raw 数组经 Qt 信号进入 GUI 事件队列，STOP 信号排在大量历史数据回调之后，用户看到 STOP 延迟数秒。
- 2026-08-12 长时间 `.bz` 保存日志证明保存没有丢数据，但 GUI Phase 显示链路 `_on_phase_data` 长期占用主线程，驱动缓冲峰值可到约 `32.65 s`。
- 2026-08-13 / 2026-08-14 高负载显示日志证明，`Length/Plot=0.4 s` 参数生效不等于界面能按 0.4 s 流畅刷新；如果每次仍准备或绘制几十到数百 MB 的窗口，主线程和内存带宽会成为瓶颈。
- 2026-08-14 100 kHz 日志证明，`.bin` 与 `.bz` 都能把应用收到的数据连续写完，但真实输出帧率约 50 kframe/s 的问题发生在 Python 读取之前，不能用“文件有 100000 帧”误判为真实 1 秒。

大数据量 DAS 软件应按以下优先级设计：

| 优先级 | 链路 | 原则 |
| --- | --- | --- |
| P0 | 采集读取 | 尽快从 DLL/驱动缓存取走数据，避免驱动环形缓冲长期积压。 |
| P0 | 本地保存 | 完整块优先入队，保存线程后台处理；保存丢弃必须显式计数和告警。 |
| P1 | GUI 显示 | 最新快照模型，允许跳显示帧；绝不能让 GUI 历史事件积压反压采集。 |
| P1 | STOP/错误处理 | 不强杀线程；识别硬件/驱动致命状态后熔断并提示现场复位。 |
| P1 | 诊断日志 | 分段记录 query/read/crop/dispatch/display/save/tcp，让现场日志能直接定位瓶颈。 |
| P2 | TCP/压缩/PSD | 后台化、限流、可丢非关键显示/通信数据；不得影响完整本地保存。 |

## 2. 数据流设计经验

### 2.1 把数据分成“完整数据块”和“显示快照”

早期结构容易把完整采集块通过 Qt 信号直接送到 GUI 主线程，再由主线程同时承担显示、保存、通信或派生处理。这个结构在小数据量下可运行，在几十 MB/块、数百 MB/s 级别时会迅速暴露问题：Qt 事件队列积压历史大数组；GUI 回调处理旧数据；STOP、错误信号、状态更新被历史显示事件挡住；采集线程为了准备显示窗口做大数组拼接，反过来拖慢 DLL 读取；主线程中的 rad 转换、PSD、Time-Space、SPACE 单点抽取放大内存带宽压力。

当前更合理的数据流是：

```text
DLL/驱动缓冲
    ↓
AcquisitionThread 读取 Length/Load 完整块
    ↓
采集侧裁剪 / 必要连续化
    ↓
完整数据处理器（非 GUI 大数组信号）
    ├─ 本地保存：优先入队，后台 .bin/.bz 写盘
    ├─ TCP 通信：轻量 ingest，后台 Length/Comm 聚合
    └─ GUI 显示：只发布最新快照，可覆盖旧快照
```

这个设计的关键是两条数据通路语义不同：完整数据块用于保存和通信，代表采集完整性，不能因为 GUI 忙而丢失或跳过；显示快照用于用户观察，代表实时感，允许覆盖旧帧，目标是低延迟看最新状态。

对应实现包括：`src/acquisition_thread.py` 内保留 `_latest_display_data` 单槽位和 `_latest_display_lock`；GUI 尚未消费旧快照时，采集线程记录 `gui_skips`，并跳过或覆盖显示快照；`src/main_window.py` 通过轻量显示唤醒信号和 watchdog 定时器消费快照；保存与 TCP 通过完整数据处理路径进入后台队列，不依赖 `_on_phase_data()` 的绘图完成情况。

### 2.2 Length 参数模型比裸帧数更适合现场调参

当前 UI 使用 Length 模型统一采集、显示、保存和通信包长：

```text
load_frames = round(Length/Load * ScanRate)
plot_frames = round(Length/Plot * ScanRate)
save_frames = round(Length/Save * ScanRate)
file_frames = round(Length/File * ScanRate)
comm_frames = round(Length/Comm * ScanRate)
```

工程收益是用户以秒理解“每次读多少、每次画多长、每包保存多长、每文件多长”；开发侧仍以帧数执行，便于和 DLL、文件格式、TCP 协议对齐；可以建立整数倍约束，避免半包、半窗口和跨块边界混乱；不同链路可以独立调节，不再用一个 `FrameLoad` 同时决定读取压力、显示压力和保存包长。

约束经验：`Length/Plot` 必须是 `Length/Load` 的整数倍，除非显示控件自己维护滚动缓冲并只消费增量块；`Length/Save` 必须是 `Length/Load` 的整数倍；`Length/File` 必须是 `Length/Save` 的整数倍；`Length/Comm` 必须是 `Length/Load` 的整数倍。

注意：Length 秒数是配置时间基准，不必然等于真实墙钟时间。2026-08-14 的 100 kHz 测试显示，100000 帧文件实际约 2 秒生成，说明硬件/DLL 可见输出约 50 kframe/s。文件名中的配置 Hz 不能直接当作真实时间轴。

### 2.3 单块大小是高负载系统的第一风险指标

大数据量问题通常不是单个算法复杂，而是单块太大导致每个环节都被迫搬运巨量内存。

```text
block_bytes = frames_per_block × points_per_frame × channels × bytes_per_sample
```

现场案例：`4000Hz / 51200点 / merge=8 / FrameLoad=4000` 每块约 `102.4 MB`；`100kHz / Length/Load=0.2s / 700点 / int32` 每块约 `53.41 MiB`；`Length/Plot=1s` 时显示窗口可达 `267 MiB`。如果还在 GUI 主线程做整块 rad 转换和绘图，卡顿是必然结果。

开发建议：启动采集时必须记录 `block_mb`、`load_frames`、`plot_frames`、`points_per_frame`；高负载下优先减小 `Length/Load`，降低单次 DLL 读取和内存复制峰值；显示窗口不要天然等于读取块；GUI 和保存队列容量不能只按块数配置，必须折算为实际字节数。

## 3. 波形刷新显示流畅性的策略

### 3.1 显示不能追求“每块都画”，应追求“低延迟显示最新块”

对实时监测软件，用户需要的是当前状态，而不是 GUI 顺序补画每一个历史采集块。补画历史块会导致显示延迟不断增长、主线程长期处理过期数据、STOP 和 Tab 切换响应变慢。

当前实现采用单槽最新快照：采集线程生成快照后放入 `_latest_display_data`，GUI 消费后清空槽位；若 GUI 未消费，采集线程记录 `gui_skips`，并跳过或覆盖显示快照。这是有意设计，不是丢采集数据。

```text
gui_skips 增加 = GUI 显示快照被跳过
save_dropped 增加 = 保存链路丢数据
tcp_ingest_dropped 增加 = TCP 通信链路丢通信块
```

三者不能混淆。

### 3.2 显示发布节流要考虑采集块到达抖动

2026-08-14 日志中，用户设置 `Length/Plot=0.4 s`，但实际 GUI 约 `0.8 s` 刷新一次。根因不是参数没生效，而是采集块实际到达间隔约 `0.390~0.409 s`，旧逻辑严格要求距离上次发布达到 `0.400 s`。如果某块在 `0.390 s` 到达，会被跳过；下一块再到达时变成约 `0.8 s` 刷新。

经验：墙钟节流不能写成刚性 `now - last >= interval`。对实时采集块，应允许小容差，例如基于 `Length/Load` 计算并限制在几十毫秒内。当前实现增加最大 50 ms 容差，实际 0.4 s 配置下容差约 30 ms，使 390 ms 到达的块也能按目标节拍发布。

### 3.3 消除“双重节流”

曾经出现的问题是采集线程按 `Length/Plot` 周期发布，GUI 又用固定或同周期定时器轮询消费。两者相位不一致时，实际刷新间隔可能放大。

当前改法：采集线程发布显示快照后发轻量 Qt 信号唤醒 GUI；GUI 定时器保留为 watchdog，不作为主要刷新节拍；显示延迟由“快照到达 + 一次 GUI 处理”决定，而不是两个定时器叠加。

经验：同一事件链路只应有一个主节拍源。数据到达驱动的刷新最好用事件唤醒；周期定时器适合作兜底。如果必须使用定时器，日志中要记录真实 `gui_interval_ms`，不能只记录设置值。

### 3.4 按当前视图发布最小必要数据

显示数据不能一律发布完整二维窗口。不同模式实际需要的数据不同：

| 显示模式 | 实际需要 | 优化策略 |
| --- | --- | --- |
| TIME 波形 | 最新几帧距离曲线 | 无滤波时只发布最新 4 帧。 |
| SPACE 模式 | 某个 Region 的时间序列 | 采集侧可只准备 region trace，GUI 侧用 NumPy 切片。 |
| PSD | 一帧或一个点的有限窗口 | 限频执行，避免每次全窗口计算。 |
| Time-Space | 二维时间-空间块 | 只在 Tab2 激活时请求；尽量发布不重叠增量块。 |
| TIME 滤波 | 可能需要连续窗口 | 按需请求完整窗口，避免默认负担。 |

对应实现：`src/main_window.py` 根据当前 Tab、显示模式和滤波状态调用 `_sync_acquisition_display_request()`；`src/acquisition_thread.py` 的 `set_display_request()` 接收显示模式、Region、是否需要完整窗口、是否需要增量全宽快照等信息；`snapshot_kind=3` 表示 Time-Space 增量二维快照，GUI 直接更新 Tab2，不再走 Tab1 波形/PSD 路径。

经验：显示请求应由 UI 状态反向告诉采集线程，而不是采集线程固定准备最大数据。Tab 不可见时，不应持续承担该 Tab 的重绘成本。“数据已采集完整”和“显示需要完整窗口”是两个不同问题。

### 3.5 延迟做单位转换和滤波

旧逻辑在 `_on_phase_data()` 中对完整显示窗口做 `int32 -> float32(rad)` 转换。高负载下，这会把几十到数百 MB 的数组在 GUI 主线程转换一遍，即使后续只画一小部分。

当前经验：保存和 TCP 保持原始 `int32`，不要为了显示提前改值；GUI 显示时传递 `phase_scale = pi / 32767`；只有真正要绘制的数据才做转换；Time-Space 在 `src/time_space_plot.py` 中先做距离裁剪、空间降采样、必要滤波、时间降采样，再乘 `display_scale`。

对应代码点：`src/main_window.py` 的 `_on_phase_data()` 不再整块转换，按显示函数需要转换；`src/time_space_plot.py` 的 `update_data(data, display_scale=...)` 与 `_build_display_block()` 中后移缩放；`src/realtime_filter.py` 是 display-only，不改变保存数据。

### 3.6 用向量化替代 GUI 主线程 Python 循环

SPACE 模式曾经用 Python 循环逐帧抽取一个空间点。在 40000 或 100000 帧窗口下，这类循环会放大 GUI 主线程耗时。当前策略是：

```python
matrix = np.asarray(display_data).reshape(frame_num, point_num)
raw_trace = matrix[:, region_idx]
```

经验：GUI 主线程不应出现大帧数 Python 循环。对 NumPy 数据，优先 reshape + slice，必要时再 `np.ascontiguousarray()`。是否复制要有明确目的：给绘图库、保存线程或 DLL 交互需要连续内存时才复制。

### 3.7 Time-Space 必须使用滚动缓冲和增量更新

Time-Space 是最容易拖垮 GUI 的显示模块，因为它天然是二维图像，并且用户常要求长时间窗口。

已形成的做法：`src/time_space_plot.py` 内部维护固定滚动显示缓冲 `_display_buffer`；新块写入缓冲右侧，满后整体左移或覆盖对应列；使用 `ImageItem.setImage()` 显示 `(space, time)` 数据；颜色范围由前面板 `vmin/vmax` 控制，避免每次刷新自动 levels 抖动；缩放、矩形放大和平移通过 `plot_interaction.py` 统一处理；Tab2 使用不重叠增量快照，避免反复发送完整历史窗口。

经验：Time-Space 控件应自己维护滚动窗口，不应依赖采集线程每次拼全窗口。图像显示要避免每次重建控件、重新绑定 Histogram 或重新分配完整历史数组。颜色范围、坐标范围和缩放状态属于显示状态，不能被数据刷新无条件重置。

## 4. 数据完整性与不丢数据策略

### 4.1 完整性必须定义边界

2026-08-14 100 kHz 测试是一个关键教训：`.bin` 文件序号连续，92 个文件，每个完整文件 100000 帧；总字节数与 `92 × 100000 × 700 × 4` 精确匹配；`.bz` 包序、CRC、文件序号均连续；保存器记录 `dropped=0`、`continuity_gap=0`。但文件名时间戳显示每 100000 帧约 2 秒才生成，无存储测试同样约 50 kframe/s。

因此可以得出的结论是：Python 应用收到的帧被连续保存了；但当前硬件/DLL 可见 PHASE 输出帧率约为 50 kframe/s，而不是配置的 100 kframe/s。不能得出的结论是：这个 100000 帧文件覆盖真实墙钟 1 秒。

开发经验：保存完整性指标应包含 `frames_received`、`frames_written`、`pending_frames`、`continuity_gap`、`dropped_blocks`；真实帧率指标应包含 `configured_fps`、`measured_fps`、`fps_ratio`、`driver_pending_frames`；文件元数据应区分 `configured_scan_rate` 与 `measured_output_fps`；当二者冲突时，真实时间轴应以 `measured_fps` 或文件名墙钟间隔校准。

### 4.2 保存链路必须后台化，采集线程只做轻量入队

保存设计目标：采集线程不等待磁盘写入，不执行重压缩；保存队列满时必须显式记录丢弃；STOP 时必须等待后台线程排空，不能提前关闭文件。

当前实现：`src/main_window.py` 的完整数据回调优先调用 `data_saver.save_block(data)`；`src/data_saver.py` 内 `.bin` 和 `.bz` 保存器使用后台线程处理聚合、降采样、写盘或压缩；`.bz` 分 raw、packet、compressed 队列，压缩 worker 并行处理；`.bin` 停止保存时等待写线程完整退出，不再固定 5 秒后关闭文件。

经验：保存入队优先于 TCP 处理。通信可以丢旧块，保存不能被通信聚合拖慢。`Save DS` 只做空间点抽取，不做时间帧删除。存储专用降采样放到保存线程，避免采集线程做大数组切片和复制。队列入队失败时必须增加 `dropped_blocks`，不能静默丢。

### 4.3 队列容量按字节预算，而不是按块数

旧的固定 `storage_queue_frames=200` 或 raw queue 200 块，在小块场景安全，在 53.41 MiB/块时理论上可能消耗约 `10.68 GiB`。这类配置容易把防丢队列变成内存炸弹。

当前策略：启动保存时根据实际 `block_mb`、`packet_mb`、`input_mib_s` 和可用内存估算队列；默认总队列预算上限约 1536 MiB，并按 raw、packet、compressed 阶段分配；日志记录 `queue_budget_mb`、`raw_backlog_s`、`bz_worker_working_set_est_mb`。

经验：队列容量不能脱离数据块尺寸。现场判断保存是否安全要看 backlog 秒数，而不仅是 queue size。高压缩包场景下，即使每阶段至少一个槽位，也可能出现最小工作集超过预算，应在日志中暴露。

### 4.4 异步保存需要明确数组所有权

大数据块如果为了保存再复制一份，会显著增加内存带宽和内存占用；但如果不复制，又存在异步线程尚未写盘时数据被其他消费者改写的风险。

当前约定：保存器成功入队后，NumPy 数组转为只读；保存/TCP 后续消费者只能读取，不得原地修改；如果队列满导致入队失败，恢复原写权限，避免调用方后续异常。

经验：大数组异步传递要么复制，要么转移所有权；不能靠“大家都小心”。只读标记是低成本防护，但要求所有需要修改的消费者先复制。测试中要覆盖“入队后尝试修改应失败”和“队列满失败后写权限恢复”。

### 4.5 `.bin` 与 `.bz` 的完整性边界不同

`.bin` 优点是裸 `int32` 连续流，写入速度快，适合高负载长时间完整保存；缺点是不自描述，没有 packet header、时间戳、CRC，离线解析依赖日志和参数。完整性主要靠文件大小、文件序号、保存器帧计数、逐值回读测试验证。

`.bz` 优点是自带文件头、packet header、包序号、CRC，离线复核能力强；缺点是压缩 CPU 和内存压力大，高负载下可能跟不上实时输入。完整性可通过 packet 序号、CRC、解压逐值一致性验证。

2026-08-14 实测：100 kHz、700 点、int32 输入约 `267 MiB/s`；本机 `.bin` 临时盘可达约 `1306.6 MiB/s`，余量较大；`.bz` 默认 1 s 包压缩约 `2683.5 ms`，4 worker、0.2 s 包持续测试有效处理约 `171 MiB/s`，低于 `267 MiB/s`。

经验：高负载长时间完整保存优先 `.bin`。使用 `.bz` 时应提高 `Save DS`、降低压缩等级、缩短 packet 或增加 worker，并用现场日志证明队列不增长。不应只看 `slow_compression_packet_count` 判断丢数据；关键是 `dropped=0`、`packet_queue_full=0`、`compressed_queue_full=0` 和停止排空。

### 4.6 STOP 时必须排空保存队列

旧 `.bin` 停止路径固定等待 5 秒后关闭文件，在慢盘或大积压时存在后台线程未结束、文件被提前关闭的风险。当前策略是 STOP 后保存器持续等待后台线程排空；每 5 秒记录等待告警，但不在写线程仍活着时关闭文件；停止摘要输出最终帧数、pending、dropped、continuity。

经验：STOP 流畅性和数据完整性有冲突时，保存完整性优先。GUI 可以立即恢复部分控件或提示“正在排空保存队列”，但不能提前关闭底层文件。测试必须覆盖慢写盘，例如单次写入阻塞 5.2 秒仍能完整保存。

## 5. 软件控制不卡死的策略

### 5.1 不要强杀采集线程

2026-05 的经验表明，强制 `terminate()` 采集线程可能让 DLL、DMA 或设备句柄处于未知状态，导致二次启动无波形或需要重启电脑。当前 `AcquisitionThread.stop()` 只请求停止，不强杀；`wait_until_stopped(timeout_ms)` 只等待线程退出；STOP 顺序尽量温和：请求线程停、停止硬件、等待线程、停止保存器和 TCP、清理 UI 状态。

经验：与硬件 DLL 交互的线程不能随意强杀。一旦 DLL 调用卡在锁内，主线程同步调用 `api.stop()` 也可能被同一锁拖住；日志要能显示当前阶段。自动恢复只适用于线程还能响应的轻度停滞，不适用于 DLL/驱动硬卡死。

### 5.2 明确识别硬件/驱动致命状态

`0xFFFFFFFF` 缓冲区查询异常是典型例子。它不是合理点数，而是底层错误哨兵值或状态残留。

当前策略：`src/pcie7821_api.py` 检查 `query_buffer_points()` 返回码和 `0xFFFFFFFF`；`src/acquisition_thread.py` 将 `PCIe7821Error` 或含 `0xFFFFFFFF` 的查询异常视为致命缓冲区查询错误；致命错误后采集线程熔断退出，不再持续刷屏；`src/main_window.py` 收到致命错误后调度 STOP 清理，并提示现场复位 PCIe 设备/驱动。

经验：硬件状态异常不能靠软件无限重试掩盖。自动 stop/start 不能替代设备断电重启或驱动重新枚举。日志应从几千行重复错误收敛为一次明确错误和处置建议。

### 5.3 底层 DLL 调用必须有阶段诊断

大数据量卡死时，最重要的问题是“最后卡在哪一步”。因此采集线程应记录当前阶段：等待缓冲区、`query_buffer_points()`、`read_phase_data()`、`read_monitor_data()`、裁剪/复制、完整数据分发、显示快照发布、停止请求。

当前 `Acq snapshot` 记录 `stage`、`stage_ms`、`buffer`、`buffer_ratio`、`backlog_s`、`query_ms`、`read_ms`、`api_read_ms`、`crop_ms`、`dispatch_ms`、`display_pub_ms`、`read_age_s`、`block_mb`、`gui_skips`、`configured_fps`、`measured_fps`、`fps_ratio`、`driver_pending_frames` 以及保存与 TCP 诊断字段。

经验：不要只在异常后打印“卡了”；要周期性记录阶段和耗时。STOP 前、stall 检测前应强制输出一次快照。现场日志必须能让开发者不接触现场电脑也能判断瓶颈层级。

### 5.4 Monitor、PSD、TCP 都应按需启用

多条辅助链路容易被低估：Monitor 波形未显示时仍读 monitor，会增加 DLL 调用；PSD 每次显示回调都算，在大窗口下会占 CPU；TCP 聚合若在采集线程执行，会拖慢保存入队和下一次读取。

当前经验：`monitor_plot_enabled` 由 UI 状态传入采集线程，未显示则跳过 `api.read_monitor_data()`；PSD 和显示转换尽量按实际渲染需要执行；Tab3 TCP 使用后台 ingest 线程，采集线程只轻量入队；TCP ingest 队列满时丢弃最旧通信块，保护采集和本地保存优先级。

原则：辅助链路可以降级、跳过或丢旧块；采集读取和本地保存不能被辅助链路长期阻塞。

## 6. 真实帧率、配置帧率与硬件边界

`docs/100kHz采样数据量减半日志分析文档.md` 汇总了多轮测试，结论是：Python 上位机没有按数据量自动把时间帧减半的路径；`.bin` / `.bz` 保存器没有对时间帧做降采样；GUI 节流只影响绘图次数，不影响保存帧数；80/100 kHz 减半发生在 Python `read_phase_data()` 之前；ClockSource 和 PolarDiv 都不是根因；不是主机 PHASE 数据吞吐上限，因为 70 kHz / Merge3 的数据率更高却能全速；50/60/70 kHz 基本全速，80/100 kHz 稳定约为配置值一半。

当前最强推断：在 `PointNum=3072、Bypass=60、DataRate=4 ns` 下，单次扫描窗口接近 `12.5 us`。70 kHz 周期可容纳，80 kHz 和 100 kHz 周期不足，固件/扫描链路可能采用隔周期输出或类似高频策略。这仍需厂商文档、寄存器回读、外部触发示波器或厂商 C/C++ 最小程序确认。

旧代码忽略硬件配置 setter 返回码，即使 DLL/固件拒绝某参数，也可能继续记录“Device configured successfully”。当前 `src/pcie7821_api.py` 检查所有关键 setter 返回码；启动 INFO 日志记录 `scan_rate`、`rate2phase`、`merge`、`polar_div` 等硬件参数；采集诊断输出 `configured_fps` 与 `measured_fps`，并计算 `fps_ratio`。

经验：硬件参数设置必须检查返回码；配置值不等于硬件实际输出值；当 `fps_ratio` 长期约 0.5 时，应优先调查硬件/固件/DLL 边界，而不是继续优化 Python 保存器。

文件命名和元数据也不能误导真实时间。如果文件名包含 `100000Hz`，开发者和用户容易认为 `100000帧 = 1秒`。但在 100 kHz 减半条件下，实际是 `100000帧 / 50000 frame/s ≈ 2秒`。因此文件名中的采样率应明确是 configured scan rate，`.bz` 文件头和日志最好增加 measured output fps，离线分析工具应允许用实测帧率校准时间轴。

## 7. 日志和测试体系经验

### 7.1 日志字段要按链路分层

推荐将日志分成以下层级：

| 层级 | 关键字段 | 目的 |
| --- | --- | --- |
| 硬件配置 | scan_rate、point_num、merge、polar_div、clock、data_rate、setter 返回码 | 判断配置是否真的被接受。 |
| DLL 缓冲 | buffer、expected_points、buffer_ratio、driver_pending_frames、query_ms | 判断驱动缓存是否积压或异常。 |
| DLL 读取 | requested、returned、read_ms、api_read_ms、block_mb | 判断读数是否短读或过慢。 |
| 采集分发 | crop_ms、dispatch_ms、save_enqueue_ms、tcp_enqueue_ms、display_pub_ms | 判断采集线程被哪条下游链路拖住。 |
| GUI | gui_interval_ms、_on_phase_data、display、rad、gui_skips、snapshot_kind | 判断显示是否流畅以及是否跳显示帧。 |
| 保存 | frames_received、frames_written、pending_frames、continuity_gap、dropped、queue_mb | 判断应用收到的数据是否完整落盘。 |
| `.bz` | raw_queue、packet_queue、compressed_queue、slow_compress、notRT、CRC | 区分压缩慢和实时链路失败。 |
| TCP | tcp_ingest_queue、tcp_ingest_dropped、tcp_process_ms | 判断通信是否影响采集或只是通信丢旧块。 |
| STOP/错误 | stage、stage_ms、read_age_s、buffer_query_error | 判断卡死点和现场处置方式。 |

### 7.2 “慢”与“丢”必须分开

项目里曾经将 `.bz` 单包压缩耗时超过 packet 对应采集时长记为 `compression_not_realtime`，容易让人误判为保存失败。但多 worker 和队列存在时，单包慢并不等于总体跟不上。

当前区分：`slow_compression_packet_count` 是单包压缩慢，属于性能指标；`compression_not_realtime_count` 是队列满、打包失败、压缩失败等明确实时链路风险；`dropped_blocks` 是实际丢保存块。

同理：`gui_skips` 不是采集丢数据；`tcp_ingest_dropped` 不是本地保存丢数据；`buffer_ratio` 高不是已经丢数据，但表示底层缓冲风险增大；文件帧数连续不是硬件真实帧率正确。

### 7.3 测试必须覆盖高风险边界

当前已有测试的价值：`tests/test_display_snapshot_cadence.py` 验证 390 ms 到达块在 0.4 s 目标节拍下不会被错误推迟到 0.8 s，验证 Tab2 增量快照不重叠和显示快照类型；`tests/test_data_saver_integrity.py` 验证 `.bin` 逐值回读、`.bz` CRC 和 packet 序号、跨文件轮转、尾包、双通道 Save DS、入队数组所有权、按字节限制队列、慢盘超过旧 5 秒阈值时 STOP 仍完整排空，以及 `frames_received == frames_written`、`continuity_gap == 0`。

后续建议增加 `tools/analyze_log.py`，自动识别采集段，输出 query/read/display/save/tcp 分位数、缓冲积压秒数、drop/error 汇总和 Markdown 报告；增加 DLL mock 测试，模拟 `0xFFFFFFFF`、短读、setter 失败、长时间 query/read 阻塞；增加离线 `.bin` / `.bz` 对比测试和大数组保存基准。

## 8. 后续类似软件的推荐架构模板

推荐线程模型：GUI 主线程只负责参数编辑、控件状态、最新显示快照消费、状态栏和日志提示；采集线程只负责 query、read、必要裁剪/连续化、完整块轻量分发和最新显示快照准备；保存线程/压缩线程负责 Save DS、Length/Save 聚合、`.bin` 写盘、`.bz` packet 压缩/CRC/写盘和 STOP 排空；TCP ingest 线程负责 Length/Comm 聚合、通信降采样、TCP 包构造和发送队列入队；绘图控件内部维护 Time-Space 滚动缓冲、颜色范围、缩放锁定和实际渲染限流。

推荐数据优先级：必须保留的是采集完整块到本地保存；尽量保留的是采集完整块到 TCP 通信；允许降级的是 GUI 波形帧、GUI Time-Space 帧、PSD 更新、Histogram 自动统计和 Monitor 辅助读取。不要让允许降级的链路阻塞必须保留的链路。

推荐用户参数包括 `Scan`、`Length/Load`、`Length/Plot`、`Length/Save`、`Length/File`、`Length/Comm`、`Save DS`、`Time DS` / `Space DS` 和文件格式。面向日志暴露派生帧数、单块 MB、输入 MiB/s、队列预算 MB、实测 fps、各阶段耗时和完整性计数。不要让用户直接填写过多内部 packet 或 queue 参数，除非处于开发调试模式。

推荐异常策略：GUI 来不及显示就跳显示帧并记录 `gui_skips`；TCP 发送/聚合来不及就丢旧通信块并记录 `tcp_ingest_dropped`；保存队列接近满要明确告警，必要时丢保存块并记录 `dropped_blocks`；`.bz` 压缩慢但队列健康只记录 slow，不判定丢数据；`.bz` 队列满或压缩失败记录 notRT/drop；DLL setter 失败时启动失败；`0xFFFFFFFF` 缓冲查询作为致命错误熔断停止；DLL 调用长时间不返回时依赖阶段日志定位，避免主线程同步长等导致 GUI 死锁。

## 9. 本项目已经形成的关键经验清单

1. 完整数据和显示数据必须分离。完整数据用于保存/通信；显示数据只保留最新快照。
2. GUI 显示允许跳帧，不允许排队补画历史大数组。
3. 采集线程不能执行重压缩、写盘、大窗口绘图、全量单位转换或 TCP 大包聚合。
4. 单块大小比总采样率更直观，启动日志必须记录 `block_mb`。
5. Length 参数模型能统一读取、显示、保存、通信语义，但真实时间仍需实测 fps 校准。
6. 显示节流要有容差，避免实际块到达抖动导致倍周期刷新。
7. 事件唤醒优于双定时器轮询；定时器适合作 watchdog。
8. Time-Space 应维护自己的滚动缓冲，尽量消费增量块。
9. 弧度转换、滤波、颜色统计应后移到裁剪/降采样之后。
10. NumPy reshape/slice 替代 GUI 主线程 Python 循环。
11. 保存优先于 TCP；通信可以后台化和丢旧块，本地保存不能被通信拖慢。
12. 保存队列容量要按字节预算，不要固定块数。
13. 异步大数组入队后要明确所有权，成功入队后设只读是低成本保护。
14. `.bin` 适合高负载完整保存，`.bz` 适合需要自描述和 CRC 的场景，但必须验证压缩实时性。
15. STOP 时保存线程必须排空，不能为了界面快速返回提前关闭文件。
16. `gui_skips`、`tcp_ingest_dropped`、`save_dropped` 语义必须分开。
17. `slow_compression_packet_count` 不能等同于保存失败，队列满和 drop 才是关键。
18. DLL/硬件 setter 返回码必须检查。
19. `configured_fps` 和 `measured_fps` 必须同时记录。
20. 文件帧数连续只能证明应用侧保存连续，不能证明硬件真实扫描频率正确。
21. `0xFFFFFFFF` 缓冲值应作为硬件/驱动异常熔断，不应无限重试。
22. 大数据量现场问题必须靠分层日志定位，不能靠主观“卡”来判断。

## 10. 后续开发建议

建议在保存文件元数据、状态栏和离线读取工具中同时呈现 configured scan rate、measured output fps、fps ratio、文件帧数和文件真实墙钟跨度估算。对 80/100 kHz 减半问题，后续应按 `docs/100kHz采样数据量减半日志分析文档.md` 中的矩阵继续验证 `PointNum`、`DataRate`、临界 Scan 和外部触发频率。

建议新增固定脚本 `tools/analyze_log.py <logfile> --output report.md`，输出采集段识别、query/read/loop/display/save/tcp 分位数、`buffer_ratio` 和 `backlog_s` 峰值、`configured_fps` / `measured_fps` / `fps_ratio`、保存完整性汇总、`.bz` 队列和压缩性能、致命错误和 STOP 阶段，以及是否满足“无保存丢块、无队列满、显示 p90 低于目标周期”的判定。

建议保留三类自动化或半自动化测试：小数组单元测试，覆盖格式、CRC、队列、所有权、尾包和轮转；大数组本机基准，模拟 `100kHz × 700点 × int32` 输入，测试 `.bin` / `.bz` 保存吞吐；硬件现场短测，每种关键参数 60 秒，检查 `fps_ratio`、`buffer_ratio`、保存 drop 和 STOP 响应。

后续修改时应避免这些回归：不要把完整采集块重新通过 Qt 信号排进 GUI 主线程；不要在 `_on_phase_data()` 入口做整块 rad 转换；不要让 Time-Space 每次请求完整历史窗口；不要让 TCP 聚合回到采集线程同步执行；不要把保存降采样移回主窗口采集回调；不要把保存 STOP 改回固定超时关闭；不要删除 setter 返回码检查和 `0xFFFFFFFF` 熔断；不要把 `gui_skips` 写成“丢数据”。

## 11. 总结

大数据量 DAS 上位机开发的核心难点，不在于某一个绘图函数或某一种保存格式，而在于多条高吞吐链路共享 CPU、内存带宽、GUI 事件队列、磁盘和 DLL/驱动状态机。经验上，系统稳定性来自清晰的数据流边界：采集线程只做实时读取和轻量分发；保存链路后台化、可验证、停止时排空；GUI 只看最新快照，按需处理最小显示数据；TCP、PSD、Monitor 等辅助链路不能拖慢采集和保存；日志必须分层记录，让每次现场问题都能定位到 DLL、采集、显示、保存、通信或硬件边界。

本项目到 2026-08-14 已经从“能采能画”的简单结构，逐步演进为“采集优先、保存可验、显示可降级、异常可熔断、日志可复盘”的结构。后续类似软件应从一开始就采用这种数据流，而不是等到大数据量现场卡顿后再拆分。
