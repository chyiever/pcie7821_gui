## 1. 结论摘要

2026-07-29 14:02 附近的软件卡死，直接卡点不在 BZ 存储，也不在 GUI 绘图，而是在采集线程调用 DLL 的 `pcie7821_read_phase_data()` 时长时间不返回。主界面 watchdog 检测到采集停滞后尝试自动恢复，进入 stop/start 流程；但 `stop()` 需要获取 `PCIE7821API` 的同一把锁，而采集线程仍卡在 `read_phase_data()` 中并持有该锁，所以 GUI 主线程也被拖住，表现为软件卡死。

15:15 和 15:22 两次重启没有成功恢复，关键证据是启动后第一次或很早一次缓冲区查询得到：

```text
buffer=4294967295/6820000
```

`4294967295` 等于 `0xFFFFFFFF`，常见含义是底层以 `-1` 或错误状态返回，但上层按无符号整数解释。它说明采集卡、驱动或 DMA 缓冲区状态在 14:02 之后没有被单纯的软件重启清干净。此时需要按设备/驱动级异常处理，例如停止采集、关闭进程、重新打开设备、重载驱动、断电重枚举或重启主机，而不是只反复重启 GUI。

本次代码已在 `query_buffer_points()` 中补充 DLL 返回码检查和 `0xFFFFFFFF` 哨兵值检查，避免把明显无效的缓冲区点数继续当成正常点数参与判断。

## 2. 14:02 卡死证据链

`20260729_100949.log` 中，异常点集中在 14:02:25 到 14:02:33 附近。关键现象如下：

- watchdog 快照显示采集线程处于 `read_phase_data` 阶段。
- `stage_ms` 从约 4.2 秒增长到约 8.2 秒。
- `read_age_s` 达到约 8.2 秒。
- 保存队列没有明显堆积。
- 随后触发 `stall_detected`。
- 主线程打印 `Stopping acquisition...` 后日志停止。

典型日志形态：

```text
stage=read_phase_data, stage_ms=4232.4, loop=13941, frames=139400000, buffer=6855288/6820000
reason=stall_detected, stage=read_phase_data, stage_ms=8226.1, read_age_s=8.2
Acquisition stall detected: no successful reads for 8.2s. Triggering auto-recovery (stop/start).
pcie7821.api : Stopping acquisition...
```

这个顺序说明 Python 层已经进入 DLL 读函数，之后 DLL 没有及时返回。若是 GUI 绘图慢，通常会看到 GUI skip 增长、绘图刷新延迟或 Qt 事件积压，但采集线程仍会持续成功读取；若是 BZ 压缩慢，通常会看到保存队列、pending frames 或非实时压缩计数增长。该日志的直接证据指向 DLL/驱动读路径。

## 3. 为什么不是 BZ 存储直接卡死

14:02 停滞快照中，存储状态接近空闲：

```text
raw_queue=0/200
compressed_queue=0/8
pending_frames=0
dropped=0
not_realtime=0
last_write_ms=10.4
last_compress_ms=381.2
```

这些指标说明：

- 原始待压缩队列没有堆积。
- 压缩后待写盘队列没有堆积。
- 没有未打包残留帧。
- 没有保存丢块。
- 没有进入非实时压缩状态。
- 最近一次写盘和压缩耗时仍在可接受范围。

因此，本次挂死不能归因于 BZ 保存线程直接卡死。不过 BZ 仍然可能增加 CPU、内存带宽和磁盘压力；如果采集块、保存包或文件时长设置过大，BZ 压缩延迟会变高。因此本次改造把 BZ 的旧帧数参数改为更直观的 `Length/Save` 和 `Length/File`。

## 4. 自动恢复为什么会把 GUI 也卡住

当前采集相关 DLL 调用由 `PCIE7821API` 内部锁保护。异常发生时路径如下：

```text
采集线程:
  AcquisitionThread -> api.read_phase_data()
  read_phase_data() 获取 PCIE7821API._lock
  调用 DLL pcie7821_read_phase_data()
  DLL 长时间不返回，锁不释放

GUI 主线程:
  watchdog 检测 stall
  _check_acquisition_stall() -> _on_stop()
  _on_stop() -> api.stop()
  stop() 也需要获取 PCIE7821API._lock
  锁被 read_phase_data() 持有，GUI 主线程等待
```

所以日志停在 `Stopping acquisition...` 是符合该锁等待路径的。软件层面的后续优化方向是：watchdog 检测到 DLL 读调用不可中断时，不应在 GUI 主线程同步执行需要同一把 API 锁的 stop 流程，而应进入异步停机、禁用继续操作、提示用户执行设备/驱动复位。

## 5. 两次重启失败的原因

`20260729_151541.log` 与 `20260729_152259.log` 的共同特征是：

- 设备 open/start 返回成功。
- 采集线程启动后第一次或很早一次缓冲区查询异常。
- 日志出现 `buffer=4294967295/6820000`。
- 随后再次进入读取停滞或停止卡住路径。

`0xFFFFFFFF` 不应作为真实缓冲区点数参与计算。它更像底层错误码或异常哨兵值泄漏到输出参数。此时软件层应立即判定设备缓冲区查询异常，停止后续读大块数据的尝试，并把错误显示给用户。

本次已补充的 `query_buffer_points()` 防护包括：

- 检查 `pcie7821_point_num_per_ch_in_buf_query()` 的 DLL 返回码。
- 返回码非 0 时抛出明确异常。
- 输出点数为 `0xFFFFFFFF` 时抛出明确异常。
- 日志中记录无效缓冲区值，便于区分“真实积压很大”和“底层状态错误”。

| --- | --- | --- | ---: | --- |

| `FramePlot` | `Length/Plot` | Tab4 | `1 s` | 从“显示帧数”改成“显示窗口时长”，允许大于 `Length/Load`，由采集线程聚合显示历史。 |

## 7. Length 参数约束

运行时换算关系：

```text
load_frames = round(Length/Load * ScanRate)
plot_frames = round(Length/Plot * ScanRate)
save_frames = round(Length/Save * ScanRate)
file_frames = round(Length/File * ScanRate)
comm_frames = round(Length/Comm * ScanRate)
```

所有 Length 参数都必须换算成整数帧，并满足：

```text
Length/Plot 必须是 Length/Load 的整数倍
Length/Save 必须是 Length/Load 的整数倍
Length/Comm 必须是 Length/Load 的整数倍
Length/File 必须是 Length/Save 的整数倍
```

默认 `Scan(Hz)=2000` 时：

```text
Length/Load = 0.2 s -> 400 frames
Length/Plot = 1.0 s -> 2000 frames = 5 个采集块
Length/Save = 1.0 s -> 2000 frames = 5 个采集块
Length/File = 10.0 s -> 20000 frames = 10 个保存包
Length/Comm = 1.0 s -> 2000 frames = 5 个采集块
```

这样设置的目的，是让 DLL 读取块保持较小，同时显示、保存和通信都可以按 1 秒窗口工作。

## 8. 各环节单包/单块数据长度

### 8.1 DLL 采集读取块

采集读取块由 `Length/Load` 决定：

```text
load_frames = Length/Load * ScanRate
```

Raw 数据单个读取块字节数约为：

```text
raw_load_bytes = Points * load_frames * Channels * 2
```

PHASE 数据单个读取块字节数约为：

```text
phase_points = Points / Merge
phase_load_bytes = phase_points * load_frames * Channels * 4
```

对于单通道 PHASE，如果启用了软件空间裁剪，采集线程从 DLL 读回完整合并后的 PHASE 数据后，会先裁剪再交给保存、通信和显示链路。因此保存、通信和显示看到的空间点数可能小于 `Points / Merge`。

### 8.2 GUI 显示窗口

显示窗口由 `Length/Plot` 决定：

```text
plot_frames = Length/Plot * ScanRate
plot_bytes = effective_points_per_frame * plot_frames * bytes_per_sample * Channels
```

当前版本支持 `Length/Plot > Length/Load`。采集线程会保存最新几个 `Length/Load` 采集块，拼出最新 `Length/Plot` 显示快照。GUI 只消费最新快照，旧快照可以被覆盖，因此显示变慢不会无限堆积历史大数组。

`Length/Plot` 不参与 DLL 单次读取大小、保存包大小和 TCP 包大小。

### 8.3 `.bin` 保存包和文件

`.bin` 使用与 `.bz` 相同的保存长度参数：

```text
save_frames = Length/Save * ScanRate
file_frames = Length/File * ScanRate
```

`.bin` 文件本身仍是裸二进制连续数据流，不写 packet header。保存器内部先把多个 `Length/Load` 采集块聚合成 `Length/Save` 保存包，再把保存包连续写入当前文件；累计到 `Length/File` 后切换文件。

单个 `.bin` 保存包原始字节数约为：

```text
bin_save_packet_bytes = effective_points_per_frame * save_frames * bytes_per_sample * Channels / SaveDS
```

单个 `.bin` 文件原始字节数约为：

```text
bin_file_bytes = effective_points_per_frame * file_frames * bytes_per_sample * Channels / SaveDS
```

其中 `bytes_per_sample` 对 Raw 通常是 `2`，对 PHASE 通常是 `4`。

### 8.4 `.bz` 保存 packet 和文件

`.bz` 也使用：

```text
packet_frames = Length/Save * ScanRate
file_frames = Length/File * ScanRate
```

区别在于 `.bz` 是自描述压缩格式，每个 packet 会携带必要元数据，并用 bitshuffle + Zstd 压缩。压缩前单个 packet 原始字节数约为：

```text
bz_packet_raw_bytes = effective_points_per_frame * packet_frames * bytes_per_sample * Channels / SaveDS
```

压缩后实际 packet 大小取决于数据特征、Zstd 等级和 bitshuffle block 设置，不能只用原始字节数精确预测。单个 `.bz` 文件目标时长由 `Length/File` 决定，默认 10 秒。

旧参数区别对应关系：

| 旧参数 | 旧含义 | 当前替代 |
| --- | --- | --- |
| `BZPacketFrames` | 一个 BZ 压缩 packet 包含多少帧。 | `Length/Save`。 |
| `BZfiles(s)` | 一个 BZ 文件包含多少秒数据。 | `Length/File`。 |
| `Blocks/File` | 一个 `.bin` 文件包含多少个 `FrameLoad` 块。 | `Length/File`。 |

### 8.5 Tab3 TCP 通信包

TCP 通信包由 `Length/Comm`、时间降采样、空间裁剪和空间降采样共同决定。流程为：

```text
多个 Length/Load 采集块 -> 聚合到 Length/Comm -> 空间裁剪 -> 空间降采样 -> 时间降采样 -> TCP packet
```

核心公式：

```text
comm_frames = Length/Comm * ScanRate
samples_per_channel = comm_frames / TimeDownsample
channel_count = selected_space_points_after_SpaceDownsample
payload_bytes = channel_count * samples_per_channel * 8
tcp_packet_bytes = 24 + payload_bytes
packet_duration_seconds = samples_per_channel / (ScanRate / TimeDownsample)
```

其中 `24` 字节是固定 TCP 协议包头，包体是大端 `float64`，每个样本 `8` 字节。

影响 TCP 包大小的参数：

| 参数 | 是否影响 TCP 包大小 | 影响方式 |
| --- | --- | --- |
| `Length/Comm` | 是 | 决定每包原始时间窗口和 `comm_frames`。 |
| `ScanRate` | 是 | 与 `Length/Comm` 一起决定原始帧数。 |
| `TimeDownsample` | 是 | 减少每通道时间样本数。 |
| `channel_start/channel_end` | 是 | 决定空间通道范围。 |
| `SpaceDownsample` | 是 | 减少空间通道数。 |
| `Merge` / PHASE 裁剪 | 是 | 决定通信链路可用空间点数。 |
| `Length/Load` | 间接 | 只作为聚合边界，要求 `Length/Comm` 是它的整数倍。 |
| `Length/Plot` | 否 | 只影响显示。 |
| `Length/Save` | 否 | 只影响保存包。 |
| `Length/File` | 否 | 只影响保存文件轮转。 |
| `Save DS` | 否 | 只影响落盘抽点。 |
| BZ 压缩参数 | 否 | 只影响 `.bz` 保存。 |

示例：

```text
ScanRate = 2000 Hz
Length/Load = 0.2 s
Length/Comm = 1.0 s
TimeDownsample = 2
空间裁剪后 1000 点
SpaceDownsample = 5
```

则：

```text
load_frames = 400
comm_frames = 2000 = 5 个 load block
samples_per_channel = 1000
channel_count = 200
payload_bytes = 200 * 1000 * 8 = 1,600,000 bytes
tcp_packet_bytes = 1,600,024 bytes
packet_duration_seconds = 1.0 s
```

## 9. 这次改造对挂死问题的影响

本次 Length 参数改造不能从根本上修复底层 DLL/驱动在异常状态下不返回的问题；这类问题仍需要设备复位、驱动修复或 DLL 支持可中断读调用。但它降低了现场误配置带来的风险：

- 默认 `Length/Load=0.2 s`，比旧的大帧数读取更保守，缩短单次 DLL 读调用窗口。
- `Length/Plot=1 s` 可以独立于读取块，显示窗口足够观察趋势，但不会迫使 DLL 一次读取 1 秒大块。
- `.bin` 和 `.bz` 使用同样的 `Length/Save=1 s`、`Length/File=10 s`，减少保存参数歧义。
- TCP 使用独立 `Length/Comm=1 s`，网络包长不再绑死在 DLL 单次读取块上。
- 参数校验会阻止非整数帧和非整数倍配置，避免半包、错位矩阵和文件轮转边界不一致。
- `query_buffer_points()` 会拒绝 `0xFFFFFFFF` 无效值，避免后续继续用异常缓冲区状态读大块数据。

## 10. 后续建议

软件侧建议：

1. watchdog 检测到 DLL 读阶段停滞时，不要在 GUI 主线程同步调用需要同一把 API 锁的 stop。
2. 对 `read_phase_data()` 和 `read_data()` 增加更明确的进入/返回日志，记录 DLL 调用耗时、请求点数、返回点数和线程状态。
3. 设备状态异常时，界面应明确提示“需要设备/驱动复位”，而不是只显示普通采集失败。
4. 保存和通信统计继续暴露 queue、pending frames、drop、compress/write/send 耗时，便于排除磁盘和网络瓶颈。

现场操作建议：

1. 高带宽测试从默认 `Length/Load=0.2 s` 或更小值开始，不要先把读取块调大。
2. 如果只想看更长的显示窗口，优先调 `Length/Plot`，不要调大 `Length/Load`。
3. 如果只想改变保存包或文件大小，调整 `Length/Save` 和 `Length/File`。
4. 如果只想改变 TCP 包时长，调整 Tab3 的 `Length/Comm`。
5. 出现 `buffer=4294967295` 后，应按设备/驱动异常处理，优先复位设备链路。

## 12. 最终判断

2026-07-29 的采集卡挂死，核心原因是底层 DLL/驱动读路径在采集卡异常状态下长时间不返回；随后 GUI 主线程触发自动恢复并等待同一把 API 锁，导致界面也卡死。15:15 和 15:22 两次重启仍失败，是因为设备/驱动状态没有被上层软件重启清干净，`0xFFFFFFFF` 缓冲区点数已经提供了明确证据。

本次代码和文档调整把旧的 `FrameLoad`、`FramePlot`、`BZPacketFrames`、`BZfiles(s)`、`Blocks/File` 统一重构为 `Length/Load`、`Length/Plot`、`Length/Save`、`Length/File`、`Length/Comm`。这不能替代硬件/驱动复位，但能让采集读取、显示、保存和通信的单包长度边界更清楚，也能减少因为参数语义混乱导致的大块读取、大包压缩或大包通信风险。
