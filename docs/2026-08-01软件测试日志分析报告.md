## 2. 总体结论

当前版本没有发现明确的进程崩溃、永久死机或无法停止采集的证据；`STOP` 后采集线程均正常退出，日志显示 `thread_stopped=True`。

排除本地硬盘满导致的写盘失败后，日志中没有发现其他 `ERROR`、`CRITICAL` 或非磁盘满类异常堆栈。

当前版本存在明确的软件侧数据保存问题：在没有磁盘满错误的 `2026-07-31 19:07:04` 至 `22:21:25` 时间段内，`.bz` 压缩持续跟不上采集节奏，保存原始队列达到 `200/200` 后发生 `32223` 个采集块丢弃。这不是今天本地硬盘满导致的失败，应按软件性能/保存链路背压问题处理。

当前版本存在明显的波形刷新卡顿：`Slow _on_phase_data` 共出现 `121426` 次，整体中位耗时约 `130.0 ms`，最大 `318.7 ms`，其中显示绘制耗时占主要部分。

数据存储也存在明显延迟和背压：`.bz` 压缩不实时警告 `3190` 次，慢写盘警告 `4523` 次，采集循环慢迭代警告 `42092` 次。非磁盘满时间段内的主要瓶颈是压缩耗时，而不是普通磁盘写入耗时。

## 5. 软件问题清单

### 问题 1：保存压缩链路吞吐不足，导致采集块丢失

- 严重程度：高。
- 证据：
  - `BZ compression not realtime`：`3190` 次。
  - `BZ raw queue full`：`32223` 次。
  - `Save enqueue failed`：`32223` 次。
  - `raw_queue=200/200`。
- 影响：
  - 已发生实际保存数据丢失。
  - 估算未保存原始块数据约 `180.45 GB`。
- 结论：
  - 这是当前版本最严重的软件问题，应优先修复。

### 问题 2：波形显示刷新耗时过高

- 严重程度：中到高。
- 证据：
  - `Slow _on_phase_data`：`121426` 次。
  - 显示刷新 `display` 中位耗时 `115.7 ms`，最大 `298.8 ms`。
  - 最大一次发生在 `2026-07-31 22:21:18.270`，总耗时 `318.7 ms`，其中 `display=298.8 ms`。
- 影响：
  - 用户会感知到波形刷新不流畅。
  - UI 线程负载可能间接影响采集状态展示和操作响应。
- 结论：
  - 显示绘制阶段是主要瓶颈。

### 问题 3：采集循环和缓冲读取存在明显延迟

- 严重程度：中。
- 证据：
  - `Slow loop iteration`：`42092` 次。
  - 期望 block 时长 `200 ms`，慢循环最大达到 `1270.9 ms`。
  - `query_buffer_points` 和 API 查询均出现大量慢调用。
- 影响：
  - 采集、显示、保存之间的实时性下降。
  - 在保存背压时，缓冲区积压进一步加剧。
- 结论：
  - 需要拆分采集、读取、显示、保存链路的性能指标，并避免某一链路拖慢整体。

### 问题 4：磁盘满时错误处理不够友好

- 严重程度：中。
- 缺陷归因：本次不计入核心软件缺陷，因为根因是本地硬盘满。
- 仍需改进：
  - 目前磁盘满后持续刷大量 traceback，日志量很大。
  - 保存失败后持续丢包，用户可能无法第一时间感知真实风险。
- 建议作为健壮性改进处理。

## 6. 建议修复方向

1. 保存链路优先修复：
   - 降低 `.bz` 压缩等级或调整压缩块大小。
   - 增加多进程或多 worker 压缩，避免单压缩线程成为瓶颈。
   - 当压缩耗时连续超过数据包时长时，立即在 UI 上报警。
   - 保存队列接近满时提前提示，而不是等到 `raw_queue=200/200` 后才丢块。
   - 提供应急保存模式，例如临时切换为未压缩或低压缩格式，优先保证不丢原始数据。

2. 数据丢失可见化：
   - 将 `save_dropped`、`save_not_realtime`、保存队列占用率放到主界面明显位置。
   - 一旦 `save_dropped > 0`，测试状态应标红并写入测试摘要。
   - 停止采集时生成保存完整性摘要，明确写出丢失块数和估算丢失时长。

3. 波形刷新优化：
   - 绘图前做可视窗口内降采样，避免每次刷新处理过量点数。
   - 限制时空图等重绘成本高的视图刷新频率。
   - 将耗时计算与 UI 绘制拆开，避免 UI 线程承担过多计算。
   - 优先优化 `display_ms`，因为日志显示它远高于 `rad_ms`。

4. 采集循环优化：
   - 将采集读取、保存压缩、UI 刷新进一步解耦。
   - 对 `query_buffer_points` 慢查询增加上下文日志，例如请求点数、返回点数、buffer 深度。
   - 当 buffer 明显超过目标窗口时，记录触发原因并在界面提示。

5. 磁盘满健壮性：
   - 开始保存前估算剩余磁盘空间是否足够完成本次测试。
   - 运行中设置磁盘剩余空间低水位报警。
   - 发生 `Errno 28` 后停止继续写同一文件，避免连续刷 traceback。
   - 明确提示“磁盘空间不足，保存已失败”，并要求用户处理后再继续保存。

## 7. 建议补充测试

1. 长时间稳定性测试：
   - 使用相同采集参数连续运行至少 `24 小时`。
   - 验证 `save_dropped=0`、`save_not_realtime=0`。

2. 保存压力测试：
   - 人为降低压缩性能或提高采集吞吐。
   - 验证队列接近满时是否提前报警，是否能避免静默丢数据。

3. 磁盘满测试：
   - 使用小容量测试盘或限额目录模拟磁盘满。
   - 验证软件是否停止保存、明确报警、避免持续刷 traceback。

4. 波形刷新性能测试：
   - 分别测试普通波形、时空图开启、时空图关闭。
   - 记录 `display_ms`、UI 操作响应时间和刷新帧率。

5. 数据完整性测试：
   - 对比采集总帧数、保存帧数、文件包计数。
   - 停止测试后自动生成完整性校验结果。

## 8. 最终判断

排除本地硬盘满后，当前版本的主要问题不是崩溃或异常报错，而是实时性能不足：

- 保存压缩链路跟不上采集速度，已经造成 `32223` 个采集块未保存。
- 波形显示刷新持续慢，显示绘制是主要耗时来源。
- 采集循环和缓冲读取存在大量慢迭代，实时性风险较高。

因此，当前版本不建议直接用于长时间、高吞吐、要求完整保存的数据采集任务。应先修复保存链路吞吐和丢数据报警，再进行长时间稳定性复测。
